# agent-record Specification

> Session record for coding agents: every past session on this machine, queryable and joined to its commits. Agents search it, and the owner measures workflow changes from it.

This document states what must hold, not how. [`docs/commands.md`](docs/commands.md) lists the commands and [`src/README.md`](src/README.md) maps the modules that meet these requirements.

## 1. Purpose & context

A coding agent's context ends at compaction, at a handoff, or when another agent takes over. The tools' transcripts on disk keep what was said, decided and done, but each tool keeps them in its own format and place, and may delete them. agent-record copies them into one archive, reads that archive into one SQLite record, and answers questions over it.

The record is what agent workflows improve from. Its first use is search: an agent finds where earlier work was said, decided or ran into friction, and reads the thread around it. Its second is the check: the signals count the friction the owner feels, week by week, and `before-after` compares them on either side of a workflow change, so the change is kept or reverted on evidence.

**Primary user:** the owner's coding agents on the owner's own machine, through the CLI and the Claude Code plugin; the owner when diagnosing the record. Not the audience: other users of the machine, remote services, teams sharing a record.

## 2. Functional requirements

### 2.1 Archive

- **FR-1** — `sync` copies every session file of Claude Code, Codex, Grok, pi and omp it finds under each tool's home into the archive, at the same path relative to the tool's root.
- **FR-2** — A session file that grew since the last sync has its new bytes added to its archive copy.
- **FR-3** — A session file that a tool deleted keeps its archive copy, and the record keeps the sessions read from it.
- **FR-4** — A session file that a tool shrank or rewrote replaces its archive copy, and the record's rows for that session are replaced by what the new copy holds. `sync` finds a changed file by its size and its change time (ctime), which every write moves, so a rewrite that keeps the file's size and modification time is found too; a file whose change time moved with its bytes unchanged is read once to compare and is not copied.
- **FR-5** — A Codex rollout that Codex moved, such as into `archived_sessions`, is moved in the archive too, and is recorded once, not twice.
- **FR-6** — The files a tool keeps beside its transcripts that the record reads (Claude subagent metadata, Grok session summaries, Codex thread titles) are archived with them.

### 2.2 Ingest

- **FR-7** — The record is read from the archive only, never from a tool's own files.
- **FR-8** — Each sync reads only the bytes an archive copy gained since the last sync.
- **FR-9** — A line still being written, with no newline yet, is not read until it is complete.
- **FR-10** — A line of a kind the record keeps that cannot be parsed, or that lacks a field its rows need (an id or a time the line records), is skipped, the rest of its file is read, and the sync reports the file and line number. A line of a kind the record does not keep is skipped without a report.
- **FR-11** — A file that cannot be read or archived does not stop the sync: the other files are read, and the sync's result lists each failure as a refusal naming its fix.
- **FR-12** — A subagent session is recorded with its parent session: the session whose tool call started it, its top-level session or another subagent of that session, where the tool records that call (a Claude subagent's metadata names it), and its top-level session otherwise. A Claude subagent recorded under its top-level session because the call that started it is not in the record is counted in the sync's report. A subagent whose parent is not in the record is recorded without one, and the sync reports it.
- **FR-13** — The record holds, per session: its tool, parent, agent type, working directory, project, branch, tool version, entry point, first and last time (the earliest and latest timestamp on any line read from its files), and title; per message: its role, time, model, text and source line; per turn: its start, end, duration, status and model; per model response: its token counts; per tool call: its tool, command or file, its git runs (each git subcommand its command ran, the directory it ran in: the session's working directory, as a `cd` or `git -C` in the command changes it, and the target a push, merge, rebase or reset names: a branch with `+`, `refs/heads/` and, for a merge, rebase or reset, `origin/` stripped, `HEAD` as written, the option for a push that sends no branch, or the ref a `--delete` names), its outcome, whether Claude Code refused it before it ran (an error result it wrapped in `<tool_use_error>`, except one saying that calling the tool errored), its times, its duration (the one Codex reports, and for every other tool the time from the call to its result), and its error text: for a call its tool reports as failed or refused, such as a Codex call that did not complete, and for a command that exited non-zero, its result's text, whole when it is 4 KB or less and otherwise its first 2 KB and last 2 KB with a marker between naming the bytes cut, masked as FR-106 says before it is cut. The record keeps no result of a call that succeeded.
- **FR-14** — A message's text that a tool wrote across several lines under one id is recorded as one message.
- **FR-15** — A model response recorded several times while it streamed is counted once, with its final token counts.
- **FR-16** — For every tool, `input_tokens` counts input tokens excluding cache reads; cache reads and cache writes have their own counts.
- **FR-17** — Each skill load is recorded once, tied to what caused it: the tool call, for a load a tool caused (the Skill tool, or a read of a `SKILL.md` that lies under a `skills/` folder at any depth, named by the folder that holds it, through Claude Code's Read tool, a Codex command, pi's and omp's `read` tool or Grok's `read_file` tool); the user's message, for a skill the user typed as a slash command; the message holding the body, for a skill an agent's definition preloads into its session. A skill is named without the plugin that qualifies it, so `acme:plan` and `plan` are one skill. A load whose skill body the transcript holds records where the skill was loaded from, and the body's length and SHA-256 as the skill's file holds it below its frontmatter: without the line naming the skill's directory, the `ARGUMENTS:` block the harness appends with what the caller passed, and the line breaks at either end. So every load of one version of a skill carries one hash, whatever it was asked. A load from a plugin's install also records that install, the directory the plugin cache names it by.
- **FR-18** — A session that ran in a Claude worktree records the checkout it belongs to as its project, and the worktree's name apart.

### 2.3 Git history

- **FR-19** — `sync` records the non-merge commits, with their author, time, subject, Conventional Commit type and changed files, of every git checkout a recorded session's working directory lies in, and labels each repo by its origin remote.
- **FR-20** — `sync` records the tracked files of each of those checkouts.
- **FR-21** — A checkout in a scratch location, such as a temporary directory, is not the owner's work and is not read.
- **FR-22** — A checkout unchanged since the last sync is not read again.
- **FR-23** — Git history is read from the checkouts on disk when `sync` runs, not from the archive. A checkout no longer on disk, including one removed while `sync` runs, is not read and is not a failure: `sync` keeps the history and tracked files it recorded before, and `rebuild` does not.

### 2.4 Rebuild

- **FR-24** — `rebuild` drops the record and reads it again from the archive, whatever schema version the record had, archiving no tool file. It first copies the record beside itself, as `<record>.agent-record-backup` or, when that is taken, the first free `-<n>` after it, and reports the copy as `backup`, so with no agent-record running, removing the record's `-wal` and `-shm` files and moving the copy over the record undoes the rebuild. A rebuild that fails after the copy names the copy as `backup` and those steps, as the refusal `rebuild_failed` carrying its cause's fix when the cause is a refusal, or as the fault `rebuild_faulted` when it is a fault. A rebuild that succeeds then removes every other copy of the record so named, so only its own stays; one that fails removes none.
- **FR-25** — After `rebuild`, every session `sync` archived is in the record as the archive last held it, including sessions whose tool files are gone. Git history is not covered (FR-23).
- **FR-26** — Given the same archive, `rebuild` writes the same session, message, turn, usage, tool-call, git-run, skill-load and hook-event rows that the syncs that built the archive wrote.

### 2.5 Schema version

- **FR-27** — The record carries one schema version.
- **FR-28** — `sync` on a record of an older schema version archives the tool files as every `sync` does, then rebuilds the record (FR-24) under its lock and reports `rebuilt` with the version it was `from`, the one it is `to` and its `backup`; every other command that reads or writes the record, except `rebuild`, refuses a record of an older schema version, and every command but `rebuild` refuses a record of a newer one.
- **FR-29** — A refusal of an older record names the next `agent-record sync`, which rebuilds it, or `agent-record rebuild` as its fix; a refusal of a newer record names upgrading agent-record the way it was installed, listing `brew upgrade agent-record`, `npm update -g @cniska/agent-record` and the installer's curl line.

### 2.6 Commands and output

- **FR-30** — Every command prints exactly one JSON line. A command that ran prints `{command, ok: true, result}` to stdout; a command refused or faulted prints `{command, ok: false, error}` to stderr and exits 1. `ok` says the command ran, not that what it judged is healthy.
- **FR-31** — Every error is either a refusal (the caller can fix it) or a fault (a bug in agent-record), and carries a code, a message, its facts, and a `resolve` naming the fix. A fault's `resolve` says to hand it to the owner.
- **FR-32** — `agent-record` with no command, or with `--help`, `-h` or `help` in its place, lists every command with its usage and summary.
- **FR-33** — An unknown command, an unknown flag, a flag without a value, a flag given twice, a wrong argument count, a blank argument and an unknown verb are each refused with the command's usage as the fix.

### 2.7 Queries

- **FR-34** — `query list` names every query with its usage and summary; an unknown query is refused, naming `query list`.
- **FR-35** — A query result carries its columns, its rows, a `denominator` sentence saying what the rows were drawn from, a `more` note when rows were cut, and a `note` saying what the rows cannot show or why the result is empty.
- **FR-36** — A query or `sql` prints a default number of rows, says when it cut rows, and prints another count when `--rows <n>` asks; a `--rows` that is not a whole number of at least 1 is refused.
- **FR-37** — `query search "<words>"` finds messages containing any of the words, ranks them by how many words matched, then relevance, then recency, and gives each hit a reference `thread` accepts.
- **FR-38** — `search` and `thread` cover only text someone said: skill bodies and text the harness injected are left out, except messages another agent or a coordinator sent.
- **FR-39** — `search` names the words that matched nothing anyone said, and, when it searches only some of the distinct words given, says how many it dropped.
- **FR-40** — `query thread` prints a session's messages, denials and tool calls in time order, given a prefix of the session's id; given a time as well, it prints the stretch around that time and says how many rows lie outside it. A denial prints its kind and the words the user gave with it, or, when they gave none, the text the agent got in place of the tool's result, such as a hook's reason. A time a query takes is an ISO time with a `Z` or an offset, to the minute or finer, such as `2026-10-14T09:00Z`, read as that instant in UTC; one without a `Z` or an offset, a date alone, or anything else is refused, naming the shape it takes.
- **FR-41** — A session prefix that matches more than one session is refused, naming matches to choose between. A prefix `agent-<id>`, as a Claude subagent's transcript file is named, also matches a subagent session as `<id>` does.
- **FR-42** — `query prior-art "<path fragment>"` lists the tracked files whose path contains the fragment, across the indexed checkouts, worktrees folded onto their checkout, the most recently committed first and a few per repo, and says when it ranked only some.
- **FR-43** — `sql "<statement>"` runs one statement against the record and returns its result in a query's shape (FR-35); a statement that would write is refused, a statement SQLite cannot run is refused with SQLite's reason, except that a statement naming a column SQLite cannot find is refused with `sql_unknown_column`, which lists the columns of each table or view the statement names, whenever it names one; a result that names a column twice is refused naming the column, and a blob is refused naming `hex()`.
- **FR-44** — `query thread` with a prefix that matches no session answers with no rows and a note saying so, not a refusal.

### 2.8 Health

- **FR-45** — `doctor` reports these checks, each `ok`, `warn` or `fail` with a detail and a fix: the record, its backup, the last sync, the launchd agent and the archive's mirror. The backup check is always `ok` and names each copy of the record a rebuild left (FR-24) with its size, or says there is none.
- **FR-46** — The record check fails when the record is missing, of another schema version, or busy, with the refusal's fix.
- **FR-47** — The sync check fails when no sync has finished, when the last sync failed, or when its outcome cannot be read; it warns when the last sync reported failed files, or finished longer ago than a threshold well past the agent's interval, which the detail states.
- **FR-48** — The agent check warns when the launchd agent is missing, runs another command than the `sync` this agent-record schedules (FR-51), or is written but not loaded.
- **FR-49** — `doctor` exits 1 when any check fails, and 0 otherwise.
- **FR-50** — Every `sync` and `rebuild` records its outcome, finished or failed, where `doctor` reads it.

### 2.9 Scheduling and plugin

- **FR-51** — `agent install` writes a launchd agent that runs this agent-record's `sync` every 15 minutes and at login, logging to the state directory, and prints the command that loads it. A release runs its `sync` by the absolute path of the command it was run as, never the file a symlink in that path leads to, so an upgrade that replaces the build behind the command leaves the agent running the new one: the npm package's command (FR-96); else the command as typed, made absolute against the working directory when it holds a `/`, or the first executable of that name on PATH when it does not; and the running binary only when neither finds one; a checkout runs Bun and its `src/cli.ts` by absolute path. A run with nothing to change says so.
- **FR-52** — Replacing an existing, different launchd agent first keeps a backup copy of it.
- **FR-53** — The Claude Code plugin starts `sync` in the background whenever a session starts, resumes, clears or compacts, and adds a note telling the agent to search the record before acting on a handoff or plan.
- **FR-54** — The plugin does nothing when `agent-record` is not on PATH.

### 2.10 Edge cases

- **FR-55** — Only one `sync` or `rebuild` runs at a time. A second is refused, naming the process that holds the record.
- **FR-56** — A lock left by a process that has ended is taken over, not refused.
- **FR-57** — Queries and `sql` read while a `sync` writes, without waiting for it to finish.
- **FR-58** — A read that cannot start because another process holds the record is refused, naming that cause, not reported as a fault.
- **FR-59** — A query or `sql` against a record that does not exist is refused, naming `agent-record sync`, and creates nothing.
- **FR-60** — A Codex token record that claims more cached input than input is skipped as malformed.

### 2.11 Mirror

The archive holds the only copy of sessions a tool has deleted, so `sync` keeps a second copy of it, the mirror, in a folder a backup service carries off the machine.

- **FR-61** — The mirror folder is `~/Library/Mobile Documents/com~apple~CloudDocs/agent-record/`, in iCloud Drive, unless `AGENT_RECORD_MIRROR` names an absolute path, which then is the mirror folder.
- **FR-62** — Every `sync` copies each archive file that its mirror copy lacks, or that differs from its mirror copy in size or modification time, into the mirror's `archive/`, at the same path relative to the archive, so the mirror holds what the archive held when that `sync` ran.
- **FR-63** — No `sync` loses what a mirror copy holds: it deletes no mirror copy, so a file the archive no longer holds, such as a Codex rollout the archive moved (FR-5), keeps its mirror copy; and before it replaces a mirror copy with a smaller archive file, an empty one included, it first sets the copy aside beside it under a name no other file has, and never empties a copy without that.
- **FR-64** — When the mirror folder's parent does not exist, as when iCloud Drive is off or a volume is not mounted, `sync` writes nothing there, reads its sessions as usual, and its result says the mirror is unreachable.
- **FR-65** — A file that cannot be mirrored does not stop the sync: the other files are mirrored, and the sync's result lists the failure with its fix (FR-11).
- **FR-66** — A `sync` that mirrored every archive file without a failure records, in the mirror folder, when it did.
- **FR-67** — No command reads a session from the mirror: `rebuild` reads the archive alone (FR-24).
- **FR-68** — The mirror check warns when the mirror folder's parent does not exist or cannot be read, when no `sync` has yet mirrored the whole archive, or when the last `sync` that did finished more than a day ago, and its detail names the mirror folder.
- **FR-69** — A `sync` whose record write fails still mirrors the archive before it reports the failure.

### 2.12 Signals

The signals count the friction the owner feels, so a change to the workflow can be checked against them. Each is read from the transcripts the record holds, except `review-findings` (FR-73) and those of §2.13, which read the hook event log. These terms hold for every signal:

- **Owner message**: what the owner typed into a top-level session. In Claude Code, a user message the transcript marks as human (or as typed or queued, before Claude Code marked who wrote it), a message the owner queued while a turn ran (FR-90), and the `[Request interrupted by user]` marker; in Codex, a typed user message in a session `codex exec` did not run; in Grok, pi and omp, every user message. A slash command, a shell escape and their output are not owner messages, and a subagent session holds none.
- **Task**: a top-level session and its subagents, from a task prompt to the next one. A task prompt is the session's start, or an owner message that comes after the agent has said something, is not an interrupt (FR-70), and was not typed while a turn ran (FR-90). A task's id is the turn id of the user message that opens it, or that message's own id where it has no turn id: the first task opens at the session's first user message, a slash command included, and a later one at its task prompt; a session with no user message gives its first task the session's id. A task is its top-level session's: two sessions whose prompts share a turn id, as a forked transcript copies it, hold two tasks.
- **Commit run** and **push run**: a git run (FR-13) of `commit` or `push` whose tool call did not fail, at the time its result came back. It counts in the repo the record holds for the checkout its directory lies in, the innermost when checkouts nest; one outside every checkout the record indexes (FR-19) counts in the repo FR-104 finds for its directory, and is not counted when it finds none. A **commit** stays what `repo_commit` holds.
- **On origin**: a commit run is on origin from the first push run in its repo at or after it, in any session. A push the owner ran outside every session is not seen.
- **Repo**: the record's repo (FR-19), shown with its label. A commit run counts in its own repo, and a task that made one in the repo of its last; an owner message and a task that made none count in the repo of the top-level session's project, found as a commit run's directory is.
- **Tag**: a `tag` line of the hook event log (§2.13) tags the task its time falls in, in the top-level session the line names, a subagent's line included. A task's tag for a key is the value of the first such line with that key; `none` when it has none. A workflow that wants a grouping, such as the route a task took, writes the tag; the record infers none.
- **Week**: Monday to Sunday in UTC, named by its Monday.

Requirements:

- **FR-70** — The `owner-interrupts` signal counts each owner message that answers, corrects or unblocks an agent, tagged by the first cause that fits: `stop`, the interrupted marker; `answer`, the last 300 characters of what the agent last said before it hold a question mark; `correct`, it opens with a word that pushes back (no, don't, stop, wait, actually, instead, why, not, wrong, undo, revert, but, isn't, shouldn't); `unblock`, it is under 80 characters and opens with a go-ahead (yes, yep, yeah, ok, okay, sure, go ahead, proceed, continue, approve, approved, lgtm, do it, ship it, push, commit). A word matches whole, case aside, and its apostrophe may be left out. An owner message before the agent has said anything, or one no cause fits, is a task prompt instead, unless it was typed while a turn ran (FR-90). A tool call the owner rejected at a permission prompt counts as `permission`. Its value is interrupts per task, over the tasks of the top-level sessions the owner typed in.
- **FR-71** — The `time-to-land` signal takes each task that made a commit run, at its task prompt, and the minutes until the task's last commit run was on origin. Its value is the median minutes over the tasks that landed; a task not landed is counted apart.
- **FR-72** — The `stranded-work` signal takes each commit run an hour older than the record's newest message, and counts it stranded when it was not on origin within the hour. A session, with its subagents, whose last commit run was never on origin is counted apart: the transcript does not say when a session is archived, so a session that ended with its last commit run unpushed stands in for it. Every commit run counts, accepted or not: the transcripts before the hook event log (§2.13) do not say. Its value is the share of commit runs stranded.
- **FR-73** — The `review-findings` signal reads the hook event log (§2.13): it takes each `verdict` line that carries its `findings`, at its time and in its hook event's place, and counts its findings by kind, its `conflicts`, and each entry of its `rules` as a citation of that rule. A verdict line without `findings`, such as one a workflow wrote before it counted them, is not counted. Its value is findings per counted verdict; by rule, each citation falls in its rule's row and every finding and verdict in no rule, so a rule's row counts its citations out of no verdict.
- **FR-74** — `query signal <name>` returns, per week, the signal's value, the count behind it, what it is out of, and the count of each cause or kind. `--by repo`, `--by version` or `--by rule` splits each week by repo, by the version a signal names, such as a step's (FR-88), or by the rule a citation names (FR-73), and `--by <key>` by the value of each task's tag for that key; `--by week` is the default, and a tag key that names one of these groups by it, not by the tag, while one that names a result column (`value`, `count`, `of`, `kinds`) is no grouping. Weeks are newest first, and within a week the row out of most comes first, then the one counting most, then the one with most events; a week, repo, rule or tag value that nothing fell in is absent, not zero. An unknown signal, and a `--by` that is neither one of these nor a tag key in the record that groups, is refused, naming the choices: these groupings and those tag keys.
- **FR-75** — `query signal-events <name>` lists each message, task, commit run, hook event, finding or skill load the signal counted, newest first, with its time, kind, repo, its task's tags, its minutes where the signal times it, the session `thread` opens, the owner's words for an interrupt, the file for a re-read, the fix, its subject and the earlier commit for an escape, the tokens and version for a step, and the rule for a citation.
- **FR-76** — `query before-after <sha>` finds the commit in the record by a prefix of its SHA and compares each signal over the `--days <n>` days (14 by default) before the commit's time with the same span after it. `--from <ts>`, a time as FR-40 reads it, starts the after window at that time instead, when the change took effect later than its commit, such as when a hook it replaced was removed. The after window ends at the record's newest message. For each signal it returns its value before and after, with the count behind each and what it is out of, so windows of different lengths compare. A prefix that matches no commit or more than one, a `--days` that is not a whole number of at least 1, and a `--from` before the commit are refused.

### 2.13 Hook events

The hook event log is the one input a workflow writes for agent-record: any Claude Code plugin's hooks may append one JSON line per decision to `events.jsonl` in the plugin's data folder (`$CLAUDE_PLUGIN_DATA`, under `~/.claude/plugins/data/`), for the decisions a transcript does not show plainly: commit and verdict gate decisions, verdicts, permission prompts and auto-mode denials. A hook never writes the record's formats; agent-record archives the log as one more source and reads it at ingest. The log begins at the first line a plugin wrote other than a `tag`, which only names a grouping, so a signal of this section counts nothing before then, and a `before-after` window that lies before it reads no event.

The format, version 1:

- The file is only appended to, one JSON object per line, and never rewritten.
- A line holds only the fields below: never a command, a prompt, a tool's input or a report.
- A field that is unknown is `null`, never missing. A kind may gain a field without a new version; a field changes meaning or goes away only with a new `v`.
- Every line: `v`, `1`; `ts`, the UTC time in ISO 8601; `event`, its kind; `session`, the session id; `agent`, the id of the subagent the hook fired in, or `null` in the main agent; `cwd`, the working directory the hook was given.
- `gate`, a gate decided whether work goes on: `gate`, `commit` (on a `git commit`) or `verdict` (on a verdict before it is recorded); `decision`, `allow` or `deny`; `reason`, a code saying why, where a commit `allow` of `accepted` says the diff is the one a verdict accepted; `repo`, the repository's absolute top level, or `null`; for a commit, `head`, the commit `HEAD` named, so the new commit is its child, and `fingerprint`, the fingerprint of the diff the gate compared with the accepted one; otherwise both `null`.
- `verdict`, a verdict on a repository's diff was recorded, one line per repository: `verdict`, `accept` or `return`; `repo`, the repository's absolute top level; `fingerprint`, the fingerprint of the diff as it stood then; and, where the workflow counts them, all three of `findings`, an object of whole counts of the findings by kind, `critical`, `major`, `minor`, `fix`, `consider` and `unrated`, every kind present; `conflicts`, a whole count; and `rules`, the rule each finding that cites one cites, one entry per finding. A line with all three `null` or left out is a verdict whose findings were not counted. Each count is at most 1000.
- `permission_prompt`, Claude Code is about to ask the owner to allow a tool call: `tool`, the tool's name.
- `permission_denied`, auto mode refused a tool call: `tool`, the tool's name; `tool_use`, the tool call's id, which the transcript also holds; `reason`, why; `rule`, the classifier rule it names, or `null`.
- `tag`, a workflow names something about the task it runs in, such as the route it took (§2.12): `key` and `value`, free text.

- **FR-77** — `sync` archives `events.jsonl` from the data folder of every plugin install, `~/.claude/plugins/data/<plugin>-<marketplace>/`, and no other file there, into the archive's `plugin-data/` at the same path relative to `~/.claude/plugins/data/`, as it archives a session file: new bytes are added (FR-2), a deleted log keeps its archive copy (FR-3), and a log shrunk or rewritten, as a reinstalled plugin starts it again, gets a fresh copy while its earlier copy stays beside it as `events-<n>.jsonl`, the first number free, and its events are the record's under that new name: the log is the only record of past gate decisions. The mirror carries it with the rest of the archive (FR-62), and `rebuild` reads it again (FR-24, FR-25, FR-26).
- **FR-78** — The record holds each line of an archived log as one hook event: its file and line, time, kind, session, agent, working directory, and the fields its kind carries. Only complete new lines are read (FR-8, FR-9). A line that is not a JSON object of format version 1, and a version 1 line of a kind the record keeps (`gate`, `verdict`, `permission_prompt`, `permission_denied`, `tag`) that lacks a field its kind requires or whose `gate`, `decision` or `verdict` lies outside the values the format lists, or whose counts are not whole numbers from 0 to 1000, or a `verdict` with only some of `findings`, `conflicts` and `rules`, is skipped and reported with its file and line (FR-10); a version 1 line of another kind is skipped without a report. `reason`, `tool`, `rule`, `key` and `value` are free text, so a new reason code is read, and a field the format adds is ignored. Another plugin's `events.jsonl` in another format is read the same way, so its lines are reported.

Terms for the signals of this section, beside those of §2.12. "Before", "after" and "between" follow the lines in time order, then by file and line, since the log's times are to the second.

- **Hook event's place**: its top-level session is the session the line names, a subagent's line included. It counts in the record's repo of the checkout its `repo` lies in, and, when that path lies in no checkout the record indexes, in the repo FR-104 finds for it or in none; a line with no `repo` counts in the repo of its session's project. Its tags are its task's (§2.12). `sync` reads each `repo` a line names as a checkout, as it reads a session's working directory (FR-19), so a worktree a hook named counts in its repo while it is still on disk, and where FR-104 places it once removed.
- **Denial**: a `gate` line whose decision is `deny`.
- **Stop**: a denial, unless the same session and agent's previous `gate` or `verdict` line was a denial of the same gate, reason and `repo`: an agent that runs the same refused command again meets one stop.
- **Reviewed commit**: a commit-gate `allow`, of any reason, before which an `accept` verdict for its `repo` was recorded in its top-level session since that session's previous commit-gate `allow` in the same `repo`. A retried commit, or one no `accept` verdict preceded, is no reviewed commit. Repos here are the paths the lines name.

Requirements:

- **FR-79** — The `false-stops` signal judges each stop and counts it a false stop when the work went on with nothing a gate checks changed. A stop after which its top-level session has no line in the log other than a `tag` is pending, listed and not judged until one follows. A commit-gate stop that carries a fingerprint (`not_accepted`, `changed_since_accept`) is upheld: the gate compared the diff, and only a recorded accept lifts it. One that carries none is a false stop when the same session and agent's next commit-gate `allow` in the stop's `repo` (their next in any repo, when the stop names none) has no verdict for its `repo` recorded in any session between the two: the agent only ran the command again. A verdict-gate stop is never a false stop, since the verdict it stopped did lack what the gate checks: it is `unfixed` when the same session and agent's next `gate` or `verdict` line is the verdict gate's `allow`, and upheld otherwise. Every other commit-gate stop is upheld. A false stop is tagged by its gate and reason, as `commit repo_unclear`, and is counted by that tag: a judged stop whose tag begins with a gate's name. It is never counted as the judged stops left over after the other judgements, so a judgement added later is not counted as a false stop unnoticed. Its value is the share of judged stops that were false stops. An owner's override, by committing in a terminal or through a shell escape, writes no line, so a stop it overrode is judged by the lines that follow it like any other. An auto-mode denial is not a stop and is not judged, since the log does not say whether the owner then allowed the call.
- **FR-80** — The `review-returns` signal takes each reviewed commit and the `return` verdicts for its `repo` in its top-level session since that session's previous commit-gate `allow` in the same `repo`, its returns. Its value is returns per reviewed commit; one more than a commit's returns is its rounds to accept. A return no reviewed commit follows is not counted.
- **FR-81** — The `blocks` signal counts each block by its source: a `permission prompt`, an `auto-mode denial`, a `commit gate` denial and a `verdict gate` denial, each denial counted, a repeated one too. Its value is blocks per task, over the tasks of Claude Code top-level sessions given at or after the log began (§2.13) and the blocks raised in those tasks; a block in a task given before the log began is not counted.
### 2.14 Skill versions

A version of a skill is its body's hash (FR-17), with the plugin install it was loaded from. Whether a version helped is read from the signals of §2.12 and §2.13 over the tasks that loaded the skill.

- **FR-82** — The `skill-usage` signal counts each skill load (FR-17), a subagent's preload too, in the task of its top-level session, and names it by its skill and version: the first 8 characters of its body's hash and its install, `-` for either the load does not carry. Its value is loads per task, over every task.
- **FR-83** — `--skill <name>`, on `query signal` and `query before-after`, counts each signal only over the tasks that loaded the skill, named without its plugin, and says so in the denominator. `before-after` also names each version of the skill that loaded on either side, with its count, and notes when the after window ran no version the before window did not, so a change not yet installed reads as such, or loaded the skill in no task. ### 2.15 What a run reported

What an agent handed back, and how its commands ended, kept beside the messages of §2.2 so a run's outcome is read from the record, not its transcript.

- **FR-84** — A subagent's hand-back report, which Claude Code carries only in the input of its `SubagentHandback` call, is the text of the assistant message that makes the call, after any text that message shows, so a subagent's report is its last assistant message text.
- **FR-85** — A shell call's exit code is recorded where its tool's transcript states one: Codex for every command; Grok for a finished shell command; omp in a result's details, which it writes for a failed command; pi and Claude Code only for a failed command, in the line pi ends its output with and the line Claude Code starts it with. A tool that states no code leaves it empty, as Claude Code and pi do for a command that succeeded, and Claude Code for a command whose non-zero exit it reports as no error, such as a search that matched nothing; it is never inferred from whether the call failed.
### 2.16 Wastes

Signals for the wastes the workflow is held to that §2.12 to §2.14 leave unmeasured, read with the terms of §2.12.

- **FR-86** — The record holds each compaction a transcript marks, with its session and time: Claude Code's `compact_boundary` line. Codex marks one too but reads files through the shell, which keeps no file path, and Grok, pi and omp mark none in the transcripts seen, so the record keeps Claude Code's alone. The `lost-context` signal takes each compaction and counts its re-reads: the files its session read with the `Read` tool since its previous compaction, or its start, and read again after it, before its next, each file once. Its value is re-reads per compaction.
- **FR-87** — The `escaped-defects` signal counts the fix commits that point back at an earlier commit, from the commit-gate hook log. A commit since the log began is gated when a commit-gate allow in its repo came at most 15 minutes before it, the allow's repo taken from its checkout or else from the commit its `head` names, and it is accepted when that allow's reason is `accepted`; a commit rebased onto a new parent counts once, and a commit no allow gated is not counted. A gated `fix` commit escaped when its subject names an earlier commit of its repo by a 7 to 40 digit sha prefix, or else when the latest accepted `feat`, `fix`, `refactor` or `perf` commit of its repo in the 2 days before it that shares a file with it came from another agent, its gate allow's agent or else its session. A test file, or a Markdown file at the repo's root, shares nothing. Each escape names the earlier commit and its minutes since it; its value is escapes per accepted commit.
- **FR-88** — The `step-cost` signal costs each step of every loop. A subagent whose agent type is namespaced, as `acme:checker`, is one step named by the part after its last colon; any other session's step is named by the skill it loaded last, preloads aside, and before its first by a subagent's agent type, or `none` for a main session. Each recorded response costs its output tokens, its input tokens with cache reads and writes, and its minutes since the latest of the session's previous response, its start, the owner's last message in it and the last return of a subagent it started, so a wait on the owner or on a subagent counts in neither. An event is a stretch of one session's consecutive responses on one step and version, cut at each owner message, with its tokens and its minutes to a tenth. Its version is the skills a namespaced subagent preloaded, or the skill a step is named by, each named with the first 8 characters of its body's hash, and none for a step named before any skill. Each event counts in its task, and a task's accepted commits are those `escaped-defects` counts (FR-87), so steps in one task share them. Its value is input tokens per accepted commit, over the accepted commits of the tasks its events fall in, so `--by version` divides a version's input by the accepted commits of the tasks it ran in; a subagent's transcript records too little output to rank by it. Each row adds output tokens and minutes per accepted commit, input, output and minutes per task, and the five steps with the most input per accepted commit.

### 2.17 Second reads

- **FR-89** — The `second-read-asks` signal counts each owner message that asks for another model's read: with its pasted blocks (`pasted_content`, `system-reminder`) left out, and unless it opens with a Markdown heading, as a pasted document does, it puts an ask verb (ask, have, get, let, task, consult, with, if, until, once, whether, give, tell, send, reframe, use, kick off) up to four words before Fable, has Fable followed by to, should, agree, approve, validate, review, design, plan, check, verify, look or decide, asks what Fable or you and Fable think, names Fable's take, opinion, view or read, or names a second opinion, a second read or a stronger model. Fable's earlier work named as a possessive, as in "fable's review", is no ask. Its value is asks per task, over the tasks of the top-level sessions the owner typed in.

### 2.18 Messages typed during a turn

### 2.20 Trace

The steps of one task, for an agent to read instead of whole transcripts.

- **FR-92** — `query tasks <id-prefix>` lists the tasks (§2.12) of the top-level session the prefix names, or that a subagent's prefix runs under, one row per task with its id, the time it starts and the head of its opening message, latest last. `query trace <id-prefix>` prints the steps of one task, one JSON line per row, in time order. For a top-level session it is the latest task, or the one `--task <id-prefix>` names: the session's steps from the task's prompt to the next, and every subagent (FR-12) whose branch under the session started in it, whole. For a subagent it is that subagent and every subagent under it, in the task its branch under the top-level session started in, and `--task` is refused. A `--task` prefix that matches no task of the session, or more than one, is refused naming the tasks to choose between. The session's `agent` step starts at the task's prompt and ends at its last line in the task, with the tokens it spent there. A line holds `at`, `session`, its `parent`, the `task` id, `seq` (the line's place among its session's lines, from 1), `step`, `phase` (`started` or `ended`), and on `ended` the `ms` since it started and an `outcome`: `{kind: ok}`, `{kind: refused, code}` or `{kind: failed, error}`; a step that has a `name` repeats it on its `ended` line, so an end reads alone. The steps are one closed list, each adding its own start and result fields: `agent`, a session, with its agent type and model, and on its end its input, cache-read, cache-write and output tokens, failed as the call that started it (FR-12) failed, and otherwise ok; `tool`, a tool call, with its id, its tool, its `target`, the skill a Skill call loads or the file path a file tool names, and `null` for any other call, a shell command included, and its `git`, the subcommands of its git runs (FR-13) in the order its command ran them, `null` for a call that ran none, refused with the tool's denial kind as its code, or with `host` when Claude Code refused it before it ran (FR-13) and gave no denial kind, and failed when it was interrupted, exited non-zero or errored; `skill`, a skill load (FR-17), with its skill's name, how it was loaded (`model`, `user`, `read` or `preload`) and the tool call that loaded it, `null` for a load no call caused, ending ok when it starts; `verdict` and `gate`, a hook event (FR-78) where the event log has one, with a verdict's repo and verdict, or a gate's gate and repo, a deny refused with its reason as its code; and `compact`, a compaction. An agent has ended, at its last line, once every tool call it made has returned; until then it, like a tool call awaiting its result, prints `started` with no `ended`. A prefix matching more than one session is refused as `thread`'s is (FR-41), and one matching none answers with no rows and a note saying so.

### 2.23 What each tool writes

- **FR-105** — A fact a tool's transcript does not write is left empty on that tool's rows, never inferred from another line. A message's origin and meta flag, a skill body, the skill a message, response or call is attributed to, a slash command, a denial with its feedback and reason, the skill a Skill call names, an interrupted call and a refused call's mark are written by Claude Code alone. Grok writes a call refused before it ran as a failed call whose text says it was not executed, with no field that tells it from an error, so the record keeps it as a failed call with that text as its error and marks it neither refused nor denied. A pi or omp response the owner aborts is a message with no call in it, so no call of theirs is interrupted. Grok, pi and omp write no turns and no turn ids, and every user message they hold is the owner's (§2.12), so their rows carry no turn, turn id or prompt source. Grok writes no token counts, and no model on a tool call. Codex ties a token record to a response and a tool call to no message, and Grok writes a tool call apart from any message, so neither links a call or a token record to a message. Claude Code's turn line names no model and no time to first token, and Codex's names no message count. A message's `extra`, the fields of its line that have no column, is kept for Claude Code and Codex, whose lines carry such fields; Grok, pi and omp lines carry none. A skill typed as a slash command, a preloaded skill and a skill's body are written by Claude Code alone, so a load on another tool's rows names no message and carries no body, path or install; Grok's load names no model, as its calls do. Compactions are scoped by FR-86.

### 2.24 Secrets

- **FR-106** — Every text the record keeps from a session file has each secret-shaped string in it replaced by `[REDACTED]` before it is written: an API key, an access token, a private key, a bearer token, a value of eight or more characters given to a key, token, secret or password name, and any value given to an environment-style name ending in `_TOKEN` or `_SECRET`, such as `CLAUDE_CODE_MESSAGING_TOKEN=`. The texts are a session's title, a message's text, extra, slash command and denial feedback and reason, and a tool call's command, file path and error text (FR-13); a git run (FR-13) is read from the masked command. The archive and its mirror stay byte copies of the tool's files (C-4, FR-2, FR-62), so a record built before a secret shape was known holds the value until `rebuild`, or the `sync` that rebuilds an older record (FR-28), reads the archive again.

## 3. Non-functional requirements

- **NF-1** — agent-record needs no credential and sends nothing off the machine itself: the mirror is a folder on this machine that a backup service, such as iCloud Drive, may carry off it (FR-61). It never reaches the network.
- **NF-2** — A sync that finds nothing new reads no session file, copies no bytes into the archive or the mirror, and reads no checkout again.
- **NF-3** — On APFS, the first archive copy of a file takes no space of its own.
- **NF-4** — No command leaves the record half-written: a file's rows and its cursor are written together or not at all.
- **NF-5** — No command crashes with an uncoded error on a common failure: a missing record, a busy record, a held lock, an unreadable or unwritable file, a missing git, a malformed tool file.

## 4. Out of scope

- Reading sessions from another machine, or sharing a record.
- Writing to a tool's files, or to the record through `sql`.
- Semantic or embedding search; `search` matches words.
- Judging quality: `prior-art` ranks by recency and commit count only.
- Restoring the git history of a checkout no longer on disk (FR-23).
- Any platform but macOS.
- Memory: distilling sessions, or putting them into an agent's context; an agent searches the record and reads what it finds.
- Gating or enforcing a workflow; the workflow's own hooks do that, and the signals only measure it.
- Keeping earlier versions of a mirror copy, other than the one set aside when a smaller archive file replaces it (FR-63).
- A command that restores the archive from the mirror; `docs/mirror.md` documents the copy back.

## 6. Deliverables

- **D-1** — The `agent-record` CLI, as a release, one executable per platform that needs no Bun and no checkout (FR-91), shipped by a GitHub release with `install.sh`, by the npm packages installed with `npm` or `bun`, and by the `cniska/tap` Homebrew formula, as [`docs/releasing.md`](docs/releasing.md) says; and as source, run by Bun from a checkout and linked onto PATH by `mise install` in the primary checkout, never in a worktree.
- **D-2** — The `cniska-record` Claude Code plugin in `plugin/`.
- **D-3** — `README.md` (install and the essential commands); under `docs/`, `commands.md` (the commands and where the record lives), `uninstall.md` (uninstall), `mirror.md` (the mirror and how to restore the archive from it), `plugin.md` (the plugin), `development.md` (development), `releasing.md` (releasing) and `trace.md` (what `query trace` shows); `AGENTS.md` (repository rules), `src/README.md` (module map), and this spec.
- **D-4** — The test suite, run by `bun run check`, and the acceptance suite in `acceptance/`, run by `bun run acceptance`. The acceptance suite drives only the CLI, and reaches past it only in two files. `acceptance/cli.ts` plants or reads state no command makes or reports without waiting real time (the record's schema version, the last-sync stamp, the mirror's time, a held lock, a held record, a write to the record that fails while a sync runs (AC-28)) or stands in for the OS (a `launchctl` or `uname` on PATH) or the network (a `curl` serving release downloads), runs the plugin's hook with an `agent-record` on PATH that tells the test when the CLI it started has exited (AC-21), runs the CLI under macOS's `sandbox-exec` with the network denied (AC-26), compiles and lays out the release that runs where no Bun is (AC-60, AC-63), and drives the npm packages through their launcher with no `node` or `bun` on PATH (AC-64). `acceptance/cli-no-wait.ts` runs the CLI with no wait for a held record, so a busy record is refused at once.

## 7. Constraints (fixed)

- **C-1** — TypeScript on Bun.
- **C-2** — The record is one SQLite database under `$XDG_DATA_HOME/agent-record/`, beside the archive.
- **C-3** — Local only: no server and no account. No command reaches the network.
- **C-4** — The archive is the source of truth for sessions; the session record is derived from it and can always be rebuilt. The mirror is a copy of the archive, never a source.
- **C-5** — Every command's output is one JSON line, for agents to read.

## 8. Open decisions (left to the builder)

- The record's tables and columns, provided FR-13 holds and a table change bumps the schema version (FR-27).
- How the archive detects that a file grew, shrank, was rewritten or moved (bounded by FR-2, FR-4, FR-5).
- How sync tells a checkout is unchanged (bounded by FR-22), and how far back a changed checkout's commits are re-read (bounded by FR-19).
- Which locations count as scratch (bounded by FR-21).
- The default row count, the number of words `search` takes, the files per repo `prior-art` ranks, and the stale-sync threshold, provided each result says what it cut (FR-36, FR-39, FR-42, FR-47).
- How search ranks within equal matched-word counts (bounded by FR-37).
- How long a command waits for a held record before it is refused (bounded by FR-58, NF-5).
- The shape of the reference `search` gives and `thread` takes (bounded by FR-37, FR-40).
- The signals' thresholds and word lists, and `before-after`'s default span, provided each is stated where the signal is defined (FR-70 to FR-73, FR-76).

### Policies chosen (not open)

- `ok` in a command's output means the command ran; a judgement it makes, such as `doctor`'s, is in its result and its exit code (FR-30, FR-49).
- A busy record is a `fail` in `doctor`, not a `warn` (FR-46).
- A busy record is SQLite reporting the database held; a race for agent-record's own lock is a separate refusal (FR-55, FR-58).
- The launchd agent's 15-minute interval is promised to the user (FR-51).
- An unreachable or stale mirror is a `warn` in `doctor`, not a `fail`: the record still works without it (FR-68).
- The mirror keeps only the archive, not the record: the record is rebuilt from the archive (FR-24).
- A release's version follows its schema: while on 0.x, a release that bumps the schema version (FR-27) is a minor release, never a patch, and the release workflow refuses a patch tag whose schema differs from the previous tag's.

## 9. Open questions and known gaps

No question is open. Every criterion is proven: each has a passing test in the acceptance suite, which drives only the CLI. `src/spec.test.ts` ties the suite to this spec. The unit tests stay unit tests and cite no ID.
